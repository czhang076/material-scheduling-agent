# 需求与验收

本文为需求基线，M1 确定性基础及 M2 存储与工具已实现；完整 Agent 仍未实现。验收依据为用户提供的小影校招第 1 题；本项目不采用三小时投入上限。

用户：内容运营与审核人员。目标：找出待处理素材，输出无冲突、可确认、可追溯的草稿。所有资料均为合成示例。

## 范围

- 输入是严格校验的 JSON：请求 ID、素材 ID、渠道、带时区的发布时间、hard/preferred 要求、时长。
- 四类核心工具：素材读取、规则检查、时段查询、草稿保存。额外支持元数据补查与结构化结束。
- CLI 为可复现评审入口，核心链路完成后补轻量本地网页工作台。单 Agent，真实接入与离线 Mock 使用同一执行器与工具。
- 每项结果包含审核状态、风险依据、原始要求、建议时段、待确认项、草稿 ID/版本/保存状态和未完成原因。
- 审核覆盖元数据与待发布文案，提供规则及原文片段证据；不实现真实发布；图片/视频只预留扩展设计，不能宣称已做视觉或完整内容安全审核。

## 必须保持的规则

1. 模型选择工具、接收实际结果后再次选择；仅离线 Mock 不能证明真实 ReAct 效果。
2. 缺失资料、阻断风险不可保存为可用草稿；人工审核风险可保存待确认草稿。
3. 硬性时段改变必须待确认；原始要求永久保留。偏好时段允许同窗口替代，仍须记录调整。
4. 时间使用带时区的绝对时刻；冲突为同渠道半开区间重叠，边界相接可用。
5. 待确认草稿不预留时段；可用草稿占用本地容量。保存及确认都必须重新校验。
6. 确认由用户通过 CLI 或后续本地网页提交草稿版本；两种入口共享同一确认用例，模型无确认工具。确认只产生可用草稿，不发布。
7. 相同请求重复执行不新增草稿；同 ID 不同输入报错；写入失败不可声称成功。
8. 资料变化或新冲突使旧草稿过期；重新审核可在同 ID 下形成新版本，旧确认不继承。
9. 工具调用数、模型轮数、总执行时间均有上限；达到上限明确返回未完成。

## 验收矩阵

|场景|必须观察到的行为|
|---|---|
|正常排期|审核通过、时段无冲突、真实保存、可用草稿|
|素材信息缺失|模型补查或请求补充；补查失败保持待补充|
|规则风险|返回规则 ID、证据及原因；阻断与人工确认分开|
|时段冲突|模型查询替代；硬性调整待确认，原要求不变|
|重复提交|重复执行仅一份草稿；内容不一致时报错|
|保存失败|返回 FAILED/未完成，无虚构草稿|
|确认闭环|版本校验、重新查冲突、明确同意后更新同一草稿|
|并发与变化|保存事务防止两份可用草稿重叠；旧草稿重新校验|
|不可靠模型|非法动作、伪造确认、过早结束及持续循环均安全失败|

## 当前工作范围

用户先要求完成设计，再在设计基线收口后要求“下一步”。当前已完成 M1 领域基础及 M2 SQLite/工具闭环，有实际保存、确认、并发和故障记录；尚无离线 Agent 或真实模型。

真实模型由用户稍后配置。后续实现先支持离线验证，不用 Mock 填充真实模型证据。

## 题面要求与项目假设

题面明确要求：四类业务工具、模型动态决策、仅草稿、硬性要求须同意后变更，以及正常/缺失/风险/冲突/重复/保存失败六项验收。

以下是项目设计假设，不是题面原文：

- 每渠道同一时刻容量为 1，按请求指定的持续时间检查区间冲突。
- READY 草稿占用本地容量；待确认草稿不占全局容量，同批候选仍互相避让。
- 确认通过可信本地用户入口发起，绑定草稿版本与全部待确认事项。
- 缺少替代窗口时只建议原始时间所在固定偏移日历日内的候选，调整须确认。
- 首版固定偏移 ISO 时间、最多 20 项、单机 SQLite；不推断自然语言日期和夏令时。
- 请求时长表示排期容量占用，不表示视频播放时长。
- 同一请求 ID 是重试身份；不同请求 ID 不做语义去重。

这些假设统一记录在详细设计中。实现时若调整，先同步受影响契约与测试计划。

## 成功标准分阶段

- P0 准备成功：目录、模块职责、数据契约、状态、确认、幂等、故障与验收计划相互一致，所有未实现明确标记。
- 功能成功：六个必验场景可运行，保存事实可核对，关键保护没有已知缺陷。
- 考核完整交付：除功能外，提供真实模型动态路径、实际输入输出/Trace、测试结果、五份完整文档、可复现运行步骤和 GitHub URL/最终 commit SHA。

当前 P0 和 M1 基础阶段已有对应检查，不能据此宣称满足完整考核。M1 结果见 [验收记录](M1-ACCEPTANCE.md)。
