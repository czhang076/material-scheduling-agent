# Agent 决策循环与预算

## 1. 执行语义

每轮由模型选择一个动作。真实模型适配器提交当前请求、工具目录和已经发生的观察；工具结果返回后，再请求模型作出下一步选择。

执行骨架只控制“校验、调用、记录、限额”，不根据冲突状态直接写死模型必须选择哪项业务动作。确定性保护可以拒绝非法保存，但不能用规则策略冒充模型决策。

逻辑步骤：

1. 校验输入，检查请求身份，创建运行清单。
2. 检查运行截止时间与剩余模型轮数。
3. 模型输出一个白名单动作及简短公开理由。
4. 校验动作和参数；拒绝项也返回实际观察，不能执行。
5. 检查工具调用余量后执行工具，保存真实结果及 Trace。
6. 将成功或失败观察加入历史，再由模型继续选择。
7. `finish`、限额、取消或不可恢复故障时组装可信结果。

## 2. 动态路径要求

|观察|合理的下一步选择|不允许的行为|
|---|---|---|
|资料有缺失且可补查|调用补查，再审核|凭描述编造版权状态|
|补查仍无资料|请求用户补充，继续处理其他素材或结束|把缺失视为通过|
|存在阻断风险|阻断该项，保留风险证据|调用确认或保存为 READY|
|时段冲突|查替代，或说明无法满足|直接覆盖硬性要求|
|替代时间可用|保存待确认建议，或在明确授权范围内保存|声称已经发布|
|保存遭遇新冲突|重新查询，或报告未完成|继续使用旧查询声称成功|
|工具临时不可用|在限额内再试、改用已支持工具或停止|无限重试或虚构结果|
|保存成功|保留结果并继续其他项或结束|重复创建新草稿|

本表是评估合理行为的准则，不是用来生成真实模型日志的固定脚本。

## 3. 系统提示的职责

完整提示正文见 [model-prompt](model-prompt.md)，六个工具的完整参数定义见 [tool-schemas](tool-schemas.md)。两者作为 v1 设计基线，提示/工具内容指纹将写入实际运行清单。

不让模型输出完整最终结果对象来控制业务状态。`finish` 的文字不得覆盖工具和存储事实。

## 4. 离线 Mock

离线模型适配器根据收到的观察选择动作，用于验证不同结果能经过同一个循环和工具。它必须标注 `model_mode=mock`，Trace 不得出现“真实模型推理有效”等结论。

另设脚本式模型替身用于对抗测试，例如跳过审核、伪造确认、不断循环。测试替身与演示 Mock 分开，避免为了让演示通过而弱化保护。

真实模型接入后，需要单独生成真实路径；HTTP 协议模拟服务只证明请求与响应适配。

## 5. 预算与超时

按合法请求项数 N（1–20）计算初始预算，避免固定 20 次调用无法处理 20 项。以下是 M3 已落实的 v1 默认值，真实模型耗时尚未验证；预算不承诺任何输入必然成功。

|预算|默认|计数与停止规则|
|---|---|---|
|每项工具尝试|10|read/check/query/save、补查、重试及该项的非法尝试全部计数|
|运行工具尝试|`min(10*N+1, 201)`|包括 finish 的一次尝试；无法归属有效项的非法动作仍消耗全局额度|
|模型轮数|`运行工具上限+4`，最高 205|每次真实调用、失败或协议解析错误都计数；不因重试重置|
|运行总时限|`min(180*N, 1200)` 秒|单调时钟；每次调用前检查并传递剩余时间|
|单次模型超时|30 秒|不超过运行剩余时间|
|同动作同参数的临时错误重试|最多 1 次|重试仍计入全局预算；没有适合重试的错误则直接反馈|

推导示例：

|请求规模|工具上限|模型轮数上限|总时间上限|正常路径基础需求|
|---|---|---|---|---|
|1 项|11|15|180 秒|读取、审核、查询、保存各一次，再 finish，共 5 次|
|20 项|201|205|1200 秒|每项四次，再 finish，共 81 次|

每项达到 10 次后标记该项未完成，模型仍可处理其他未超限项。全局预算不能因切换项而重置；finish 不归属某项。运行预算可由本地配置收紧，必须明确记录生效值；模型不能提高预算。

最多容许 4 次协议错误，之后返回 MODEL_PROTOCOL_ERROR；该阈值不额外增加模型总轮数。网络失败同样消耗轮数和时间，恢复不得静默切换 Mock。

调用次数必须在派发前预占，避免“最后一轮”突破上限。原样无限循环受到调用数和时间双重约束。单次合法动作只有一个工具调用，限制模型并行调用以简化可追踪性。

Trace 区分工具尝试数与实际执行数，拒绝参数的尝试不记作工具执行成功。每项/全局限额、拒绝和超时都保留停止或缺口原因。

达到限额返回 `stop_reason=LIMIT_REACHED`，保留已保存草稿，列出未处理项。不能把已完成一部分包装成全部完成。

本地数据库写入应设置忙等待上限。对操作系统无法中断的极端 I/O，不能保证精确硬截止；首版不宣称生产级进程强杀能力。

## 6. 模型故障与适配

- 协议错误：给模型可修正的简短观察，受轮数约束；不自动执行自由文本。
- 网络不可用：返回明确错误，在预算内按错误类型恢复；不会偷偷切换 Mock。
- 多个工具调用：首版拒绝整轮并要求单动作，避免部分执行后难以重建顺序。
- 模型最终声称保存成功：仍依据实际数据库和工具结果输出。
- 接口密钥缺失：在真实模式启动时失败；Mock 模式不要求密钥。

## 7. 如何证明是动态决策

真实模型阶段至少保留正常与冲突两条路径（M4 已有实际记录），记录模型标识、实际动作、工具参数、观察及下一动作。再改变占用时段重新运行，核对动作是否变化。

验证对象是可公开的动作和结果，不要求内部思维过程。最终结果正确但动作记录无法证明模型接收过工具结果，仍不足以验收 ReAct。

## 8. M3 落地说明

M3 已实现循环及预算；M4 增加原生工具调用适配和 DeepSeek 真实记录。模型接口为 choose(ModelContext, timeout_seconds)，返回单个 tool/arguments JSON，拒绝多动作。工具 Schema 从应用层与执行参数同源生成，实际提示与 Schema 均写入运行指纹。

工具失败由提供者读取观察后决定是否重试；执行器不自动选择业务动作。相同动作和业务参数在本轮累计两次临时失败后拒绝进一步尝试（rationale 不参与重试身份），并受全局预算约束。Trace 记录尝试/派发/执行数和实际返回。

单项到限且没有终态草稿/明确阻断/资料缺口时，最终结果列 ITEM_LIMIT_REACHED；其他项仍可处理。全局上限及总截止时间为 LIMIT_REACHED，单次提供者超时为 MODEL_TIMEOUT。最终账本不可读为 RESULT_UNAVAILABLE。调用后检查时限，迟到动作丢弃；已提交工具结果仍如实保留。具体测试和限制见 [M3 验收](../M3-ACCEPTANCE.md)。
