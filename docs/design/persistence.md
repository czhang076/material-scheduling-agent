# 持久化、幂等与一致性（设计稿）

## 1. 本地事实源

素材、规则、可提供时段和既有排期由合成 JSON 显式导入 SQLite。保存和确认只读取同一数据库中的事实，避免事务内一边锁数据库、一边读取已经变化的外部文件。

导入是用户或评测环境操作，不暴露给模型。导入失败整体回滚；素材内的文字不能发起导入或修改既有排期。

## 2. 拟定数据实体

下表保留逻辑模型。M2 已落地 SQLite：素材/补充资料/规则/时段/既有排期合并为 catalog 中的单个完整校验快照；requests、drafts、confirmations、reservations、audit_events 和 operation_receipts 单独建表。runs 留到 M3。小型整体导入减少拆表复杂度，事务仍读取同一事实源；实现见 adapters/sqlite_store.py。

|实体|关键身份/字段|用途与约束|
|---|---|---|
|requests|request_id、payload_hash、原始及规范化请求|请求 ID 唯一、业务内容不可变|
|materials|material_id、revision、metadata、来源|当前素材事实|
|metadata_supplements|source_id、material_id、fields、revision|可补查事实与来源|
|rule_sets|rule_set_id、version、content_hash、规则|当前适用规则与指纹|
|slot_offers|offer_id、channel、start、end、revision|可建议时段，不等于已占用|
|external_bookings|booking_id、channel、start、end、revision|合成的已有排期|
|drafts|draft_id、request_id、item_id、version、candidate、state、证据|唯一 `(request_id, item_id)`|
|confirmations|confirmation_id、草稿版本、接受事项、actor、指纹|确认操作身份唯一，绑定具体版本|
|reservations|draft_id、channel、start、end|仅 READY 草稿持有；与草稿同事务更新|
|audit_events|event_id、对象 ID、前后版本、原因、关联运行|保存、确认、失效等业务审计|
|runs|run_id、request_id、模式、预算、停止原因|运行摘要，不代替逐步 Trace|

所有时间持久化为可比较的 UTC 时刻，同时保留请求原始偏移。开启外键检查。版本为单调递增整数。

## 3. 请求指纹

业务请求经过严格校验后规范化：

1. 时间归一化为相同精度的 UTC；显式窗口相同时，等价偏移表示不应制造新业务请求。未给窗口时，先按原始偏移解析默认日历日窗口，把这个有效窗口也纳入指纹；不能忽略会改变搜索范围的偏移差异。
2. 对象键顺序不影响指纹；items 按稳定 item_id 排序。字符串不做可能改变业务含义的模糊清洗。
3. 包括素材、渠道、原始时间、时长、模式及替代窗口；忽略运行 ID、Trace 路径等运行元数据。
4. schema 版本纳入规范化语义，序列化后计算 SHA-256。

相同 request_id：

- 指纹相同：允许重复执行和重新核验，不创建第二份对应草稿。
- 指纹不同：返回 `REQUEST_ID_CONFLICT`，不能覆盖原请求或悄悄换成新 ID。

同样内容使用不同 request_id 暂视为独立业务请求，不做语义去重。READY 草稿的时段冲突仍会阻止重复占用。调用方必须在重试时复用请求 ID；此边界须写入 README。

## 4. 保存事务

拟用 `BEGIN IMMEDIATE` 串行化写入，在同一事务中：

1. 检查请求身份和目标项归属。
2. 读取当前素材、规则与候选定义，重新形成审核事实。
3. 验证本次运行已观察到相关审核和候选；观察快照失效则返回 `STALE_REVIEW`。
4. 检查候选范围、渠道、完整时长与硬性要求；自动计算待确认事项。
5. 查询已有排期、其他 READY 占用，以及同一请求中的其他待确认候选；排除当前草稿自身。
6. 计算草稿状态。READY 写入占用；待确认不写全局占用。
7. 按唯一请求项创建或更新同一草稿；合法重复返回 REUSED，不增加版本。
8. 草稿、占用与业务审计一并提交，再返回持久化结果。

任何步骤失败均不产生新的合法草稿。事务内不调用模型或网络工具，避免长期持锁。

唯一约束解决“同一项写两份”；区间查询加串行事务解决“不同项写入重叠时段”。不能只依赖草稿 ID 唯一性。

## 5. 并发场景

请求 A、B 均曾查到 19:00 空闲：

- A 先保存 READY，提交本地占用。
- B 获得写事务后重新查到 A，返回 `SLOT_CONFLICT`，模型可再查其他时段。

两个不同请求都保存 19:00 待确认建议：允许，因为它们不预留容量。只有先完成确认且复核通过的一方可变为 READY；另一方确认必须失败并重新规划。

同一批请求的两个待确认项应互相避让。其目的在于保证同一份方案内部可确认，不暗示跨请求全局保留候选。

## 6. 资料变化与过期

草稿保存 `material_snapshot_hash`、`rule_set_hash`、候选身份和版本及待确认事项。

- 素材或适用规则改变：重新核验，旧草稿进入 STALE；不能继承旧人工同意。
- 外部排期改变但不影响该候选：复核后可保留原草稿状态，无需无意义重建。
- 外部排期与候选冲突、候选被撤回：旧草稿进入 STALE，释放自身占用。
- 仅描述性审计字段变化是否影响快照，必须由规范化规则明确，不能随意忽略审核相关字段。

显式数据导入、补查、时段查询、保存、snapshot 检查和用户确认触发复核；仅 register_request 不执行草稿复核。没有后台守护进程；离线数据库外的真实平台变化不可见。

过期后重新规划沿用同一草稿 ID，增加版本。旧版本保留在审计中，不能原地抹掉曾经的确认或保存记录。

## 7. 确认幂等

确认包含独立 `confirmation_id` 与操作内容指纹。相同 ID、相同内容重复确认：查询已有确认并复核当前草稿，不新增第二条同意或占用。相同 ID 换内容则报冲突。

首次确认检查预期版本；重复确认可以引用同一已执行操作，但必须返回当前草稿事实。如果原同意对应的草稿后来过期，返回过期状态，不能沿用历史成功冒充当前可用。

## 8. 保存失败与结果不确定

|失败位置|期望状态|恢复方式|
|---|---|---|
|校验或写入前明确失败|FAILED；新草稿不存在|修正问题后复用请求重跑|
|事务内故障且确定回滚|FAILED；原有数据不变|重新核验后重跑|
|提交可能成功但确认响应丢失|先查证，查不到则 UNKNOWN|核对本次 operation_id 的事务内回执及当前草稿；旧草稿不能证明本次成功|
|数据库不可读，无法确认提交结果|UNKNOWN|明确待核验，禁止盲目新建|

处理写入异常时要区分“失败”与“无法确定”。只有读到符合本次目标版本和内容的持久化事实，才能把 UNKNOWN 恢复为已保存。

## 9. Trace 与业务事务（M3 已实现）

草稿、确认、占用及 audit_events 在同一数据库事务中提交；JSONL Trace 是运行证据，不承担防重复职责。M3 已实现持久 Trace 写前意图和写后失败的事实保留，下述防护有相应测试，见 M3 验收。

写操作前 Trace 故障则拒绝继续派发写工具；写操作已提交后 Trace 写失败，结果仍如实报告草稿已保存，并额外标记 `trace_complete=false` 和证据缺口。重跑时依靠业务审计和幂等性恢复，不能为了补日志再创建一份草稿。

## 10. 边界

SQLite 适合本地评审和单机并发。此设计尚未完成性能、断电恢复或高可用验证；不宣称生产级调度系统。READY 的保证限定于本地账本和最近核验时刻。
