# 审核、草稿与确认生命周期（设计稿）

## 1. 四种状态必须分开

一个素材不能只有一个含混的 `success`：

|维度|状态|含义|
|---|---|---|
|审核|`NOT_CHECKED / PASS / NEEDS_INPUT / NEEDS_REVIEW / BLOCKED`|当前资料能否支持形成排期|
|排期|`NOT_QUERIED / AVAILABLE / CONFLICT / NO_CANDIDATE`|本次观察时的时段情况|
|草稿|`ABSENT / PENDING_CONFIRMATION / READY / STALE`|持久化草稿当前是否可用|
|本次保存|`NOT_ATTEMPTED / CREATED / REUSED / UPDATED / FAILED / UNKNOWN`|这次执行对保存的实际观察|

`READY` 仅表示本地可用草稿。任何状态都不表示已发布。

## 2. 审核优先级

相同素材可能同时缺资料又存在风险。完整保留所有发现，再按 `BLOCKED > NEEDS_INPUT > NEEDS_REVIEW > PASS` 形成总审核状态。

- `BLOCKED`：明确禁用风险，禁止保存为排期草稿，禁止用确认绕过。
- `NEEDS_INPUT`：缺少必要事实，先补查；仍缺时请求用户补充，禁止猜测。
- `NEEDS_REVIEW`：已知事实触发可人工确认风险，可形成待确认草稿。
- 用户接受可确认风险后，保留 NEEDS_REVIEW 和风险证据，并记录接受事项；不会把人工同意改写为规则 PASS。
- `PASS`：规则范围内未发现阻断或缺口；不代表真实内容安全的全面保证。

例如“版权状态缺失”与“版权明确争议”分别是资料缺口与阻断风险，不能混为一谈。

## 3. 草稿状态转移

|原状态|事件与前置条件|新状态|
|---|---|---|
|ABSENT|审核 PASS，候选可用，符合已授权时间范围|READY|
|ABSENT|候选可用，但硬性时间变化或存在人工确认风险|PENDING_CONFIRMATION|
|PENDING_CONFIRMATION|同一方案重复保存，相关证据未变化|保持原状态和版本|
|PENDING_CONFIRMATION|用户确认当前版本、逐项同意、复核通过|READY，新版本|
|PENDING_CONFIRMATION|候选或相关证据变化|新版本待确认，旧确认失效|
|READY|重复运行、相关证据及占用复核通过|保持原状态和版本|
|READY 或 PENDING_CONFIRMATION|素材/规则变化、候选不再提供或出现冲突|STALE，释放自身占用|
|STALE|重新审核并保存合法方案|同一草稿 ID 的新版本；按当前条件决定 READY 或待确认|

保存失败不形成“失败草稿”来冒充已保存；它是本次操作的失败或未知结果。原有草稿可能仍存在，必须独立报告。

## 4. 时间约束

- `hard`：原始时间为硬性要求。任何不同时间都必须进入待确认。
- `preferred`：用户明确提供替代窗口时，模型可在该窗口内选择无冲突时段；否则调整仍待确认。
- 用户提供的替代窗口限制候选搜索；对 hard 要求，它不等于已经同意变更。
- 未提供窗口时，默认只建议原始时间所在固定偏移日历日中的候选，不跨日；任何调整均待确认。这是项目暂定产品假设。
- M1 明确“不跨日”限制候选开始日期；原始要求及合法候选按实际持续时间可结束于午夜后。显式窗口仍要求整个占用区间落入窗口。
- 如有窗口，候选整个区间必须落在窗口内。改变窗口或原始要求应创建新请求。
- 时间比较基于 UTC 的半开区间 `[start, end)`；相接不冲突，同渠道重叠即冲突。

默认一天内的建议范围属于可调整设计，不是题面明文要求；实现前按此文统一，不得在代码中另设隐含放宽。

## 5. 待确认事项

每项使用稳定 ID，例如：

- `TIME_CHANGE`：原始 18:00 → 建议 19:00。
- `RISK:R-MEDICAL-001`：具体规则、证据和风险说明。
- `TIME_RANGE_UNSPECIFIED`：偏好时间未给允许调整范围。

确认必须明确接受当前草稿的全部待确认 ID。不能用一个模型生成的 `approved=true` 消掉它们。阻断或资料缺失不能被列成“同意即可放行”的事项。

## 6. 可信确认入口

拟实现用户命令接收：草稿 ID、预期版本、接受的事项 ID、确认者标签、可选备注。

原子流程：

1. 读取草稿并检查版本；旧版本返回 `DRAFT_VERSION_CONFLICT`。
2. 检查逐项同意是否完整；缺少任何事项均不更新。
3. 读取最新素材、规则与候选；相关证据改变则失效，要求重新规划。
4. 检查现有排期和其他 READY 草稿；冲突时返回 `SLOT_CONFLICT`。
5. 更新同一草稿、增加版本、写确认记录与本地占用。

CLI 操作者视为本地可信用户；后续本地网页通过受限 HTTP 入口调用同一确认用例。确认者标签仅用于审计，尚不提供多人身份认证。本地网页仍需同源和会话防伪；若扩大为可被其他人访问的服务，必须另设计认证授权。

## 7. 批量请求

各项独立审核和保存，保留已成功结果。某项失败不回滚其他合法草稿。

同批待确认候选也要互相避让，防止交付一份内部已经冲突的方案；不同请求之间的待确认草稿不预留容量。后续确认时通过事务解决竞争。

## 8. 任务状态聚合

- 全部素材拥有经本次核验的 READY 草稿：`READY_DRAFTS`。
- 全部已有草稿且至少一项待确认，其余 READY：`NEEDS_CONFIRMATION`。
- 混合成功、阻断、缺失或失败：`PARTIAL`，逐项结果是判断依据。
- 无可用成果：按实际原因返回 `NEEDS_INPUT / BLOCKED / FAILED / INCOMPLETE`。
- 限额到达后即使部分草稿已保存，运行仍标 `LIMIT_REACHED`，保留全部逐项事实。

任务状态、停止原因和逐项状态是三个字段。模型主动结束并不自动等于任务完成。
