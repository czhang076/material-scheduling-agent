# AI辅助、个人参与与验证记录

本项目使用Codex辅助开发。下文分别记录候选人的实际参与、AI辅助范围、设计修改和验证结果；核心设计及复盘见 [总体方案](02-solution.md)和 [设计与实现复盘](05-retrospective.md)。

## 个人参与与实际投入

候选人确定第1题及业务目标，要求先完成架构和设计，再推进实现；明确选择“元数据与文案审核、保留图片/视频扩展设计”及“CLI核心完成后补本地网页”。随后选择DeepSeek并授权接入，要求最终审查、修复、严格复跑和GitHub公开交付。范围选择见 [决策清单](DECISIONS.md)。

候选人于2026-10-31自报个人累计投入约4小时，为估算，未连续计时；该时长记录个人投入，不由消息跨度或AI运行时间换算。

## 关键设计修改与验证

|问题或取舍|项目采用的处理|实际验证|
|---|---|---|
|完成状态不能只用一个success表达|分别保存审核、草稿、用户确认、保存尝试和执行状态|风险、待确认、UNKNOWN及Trace故障场景分别检查业务事实和运行结果|
|查询空闲后可能被其他请求占用|保存及确认在SQLite写事务内重新审核、核对版本和占用|双连接竞争、保存前占用变化、待确认草稿竞争确认的回归|
|重复操作与重新规划需要同时支持|请求身份不可变；同请求项沿用草稿ID，变更建议时增加版本、清除旧授权|重复提交保持一份草稿；新增19点占用后建议20点，仍待确认|
|写入完成但回执丢失|草稿、预留、审计和操作回执同事务保存；无法查证时返回UNKNOWN|提交后故障及回执查询失败场景核对数据库与当前保存尝试|
|真实工具协议不能靠预设日志替代|保留原生tool_call_id，将实际观察按原ID返回模型|逐动作匹配服务回执、Trace和保存事实；Mock与真实证据分开|
|前端重试混淆原要求与新输入|原提交保留独立身份和模式，提供查询/重试原提交入口|修改输入和模式后的未知提交控制器用例|
|终态日志故障及旧响应串线|终态降级与显式对账；按运行ID、加载代次和事件序号隔离异步响应|M6终态恢复与7项Node状态用例|

这些设计取舍的业务原因、代价和改进过程见 [复盘](05-retrospective.md)。候选人的范围调整与授权记录在本页前文，技术实现及运行证据按实际来源记录。

## 验证结果与证据范围

- M1领域基础：70个方法；[M1验收](M1-ACCEPTANCE.md)。
- M2工具与SQLite：113个方法、7组实际工具案例；[M2验收](M2-ACCEPTANCE.md)，尚无模型决策结论。
- M3离线循环与CLI：156个方法、14组离线场景16次运行；[M3验收](M3-ACCEPTANCE.md)，明确为Mock。
- M4真实接入：184个方法、7次DeepSeek运行36次调用；[M4验收](M4-ACCEPTANCE.md)。
- M5网页：214个方法、实际HTTP/浏览器案例及1次真实网页运行5次调用；[M5验收](M5-ACCEPTANCE.md)。
- M6审查修复：222个方法、另7项Node状态用例；[M6验收](M6-ACCEPTANCE.md)。
- 最终独立验收：干净源码重建wheel、全新环境安装，222个方法无跳过；另7项Node用例、14组离线16次运行、6组HTTP业务及1组恢复；新增当前应用代码8次真实CLI和2次真实网页运行，共51次DeepSeek调用。见 [最终验收](FINAL-ACCEPTANCE.md)及 [原始证据清单](../examples/final-acceptance/manifest.json)。

各阶段测试数量为累计快照，不能相加。真实模型的有限合成案例不代表通用成功率。技术验收时尚未补录的用时和GitHub字段保持原始值；后续用时补录及 [公开交付](GITHUB-DELIVERY.md)另有记录。

## 交流与复盘

候选人在交流中判断：候选时段出现新冲突后不应继续保存旧建议，应重新寻找空闲时间。随后围绕SLOT_CONFLICT、事务内复核、模型与工具的职责开展代码讲解。

正常与重复请求的引导实验已由Codex在独立本地账本执行，实际观察到CREATED变为REUSED、草稿ID/版本不变、草稿及预留各一份；该实验用于辅助理解业务状态，采用Mock。候选人对该实验的解释仍在交流中，不将已提供讲解直接记录为独立发现或掌握验证。

后续复盘按“观察到的现象→解释依据→实际修改→验证结果”追加，分别标记本人操作、AI执行和共同讨论。个人掌握情况以实际回答、代码阅读和操作为依据。
