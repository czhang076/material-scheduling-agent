# AI辅助、个人参与与验证记录

本项目使用Codex辅助开发。本文说明我的项目参与、AI辅助方式，以及关键设计修改和验证结果；核心方案与取舍见 [总体方案](02-solution.md)和 [设计复盘](05-retrospective.md)。

## 个人参与与实际投入

我选择第1题，希望围绕内容团队的素材审核和排期需求，完成一条可运行、可确认、能用证据核对的核心链路。推进过程中，我重点参与了以下工作：

- **明确实现范围**：选择元数据与文案审核，保留图片/视频扩展设计，使首版能够集中验证审核依据、时段冲突和确认边界。
- **确定开发顺序与展示方式**：先完成仓库架构和设计文档，再实现CLI核心，随后补充轻量本地网页工作台。
- **确定真实模型接入**：选择DeepSeek并提供本地访问配置，支持真实模型路径验证和独立的离线Mock入口。
- **推进审查与交付**：提出最终审查、问题修复和独立复跑要求，要求再次逐项核对题面，并选择公开GitHub仓库便于评审读取。
- **完善交付表达**：提出补充核心设计决策、优化个人参与说明的意见，使材料更直接地呈现业务思考、设计取舍和验证过程。

个人投入约4小时（估算，未连续计时）。具体范围选择见 [决策清单](DECISIONS.md)，验收及交付结果见 [最终验收](FINAL-ACCEPTANCE.md)和 [GitHub交付](GITHUB-DELIVERY.md)。

## 关键设计修改与验证

|问题或取舍|项目采用的处理|实际验证|
|---|---|---|
|完成状态不能只用一个success表达|分别保存审核、草稿、用户确认、保存尝试和执行状态|风险、待确认、UNKNOWN及Trace故障场景分别检查业务事实和运行结果|
|查询空闲后可能被其他请求占用|保存及确认在SQLite写事务内重新审核、核对版本和占用|双连接竞争、保存前占用变化、待确认草稿竞争确认的回归|
|重复操作与重新规划需要同时支持|请求身份不可变；同请求项沿用草稿ID，变更建议时增加版本、清除旧授权|重复提交保持一份草稿；新增19点占用后建议20点，仍待确认|
|写入完成但回执丢失|草稿、预留、审计和操作回执同事务保存；无法查证时返回UNKNOWN|提交后故障及回执查询失败场景核对数据库与当前保存尝试|
|真实工具协议不能靠预设日志替代|保留原生tool_call_id，将实际观察按原ID返回模型|逐动作匹配服务回执、Trace和保存事实；Mock与真实证据分开|
|前端重试混淆原要求与新输入|原提交保留独立身份和模式，提供查询/重试原提交入口|修改输入和模式后的未知提交控制器用例|
|终态日志故障及旧响应串线|终态降级与显式对账；按运行ID、加载代次和事件序号隔离异步响应|M6终态恢复与7项Node状态用例|

这些设计取舍将业务要求落实为可检查的状态、权限和数据约束。相关原因、代价和改进过程见 [复盘](05-retrospective.md)，并与上文的范围选择、AI辅助方式及实际运行记录对应。

- M2工具与SQLite：113个方法、7组实际工具案例；[M2验收](M2-ACCEPTANCE.md)，尚无模型决策结论。
- M3离线循环与CLI：156个方法、14组离线场景16次运行；[M3验收](M3-ACCEPTANCE.md)，明确为Mock。
- M4真实接入：184个方法、7次DeepSeek运行36次调用；[M4验收](M4-ACCEPTANCE.md)。
- M5网页：214个方法、实际HTTP/浏览器案例及1次真实网页运行5次调用；[M5验收](M5-ACCEPTANCE.md)。
- M6审查修复：222个方法、另7项Node状态用例；[M6验收](M6-ACCEPTANCE.md)。
- 最终独立验收：干净源码重建wheel、全新环境安装，222个方法无跳过；另7项Node用例、14组离线16次运行、6组HTTP业务及1组恢复；新增当前应用代码8次真实CLI和2次真实网页运行，共51次DeepSeek调用。见 [最终验收](FINAL-ACCEPTANCE.md)及 [原始证据清单](../examples/final-acceptance/manifest.json)。

各阶段测试数量为累计快照，不能相加。真实模型的有限合成案例不代表通用成功率。技术验收时尚未补录的用时和GitHub字段保持原始值；后续用时补录及 [公开交付](GITHUB-DELIVERY.md)另有记录。

## 复盘讨论与实例

复盘讨论从“查询时空闲，保存前被其他请求占用”这一场景展开。我判断此时不能继续保存旧建议，应重新寻找空闲时间；随后结合SLOT_CONFLICT返回、事务内复核和执行器反馈，梳理模型决策与工具约束之间的分工。

正常与重复请求的导读实验由Codex在独立本地账本执行，实际结果为CREATED变为REUSED、草稿ID/版本不变、草稿及预留各一份。该实验采用Mock，用于讲解业务状态与防重复；后续讨论围绕“重复运行如何复用草稿，以及为什么应排除自身预留”继续展开。

上述实际判断、追问、代码解释及实验对照已整理为 [学习复盘](06-learning-review.md)，导读实验的原始输入、两次输出和Trace另存于 [examples/learning-review](../examples/learning-review/manifest.json)。新增评估器的连接关闭问题、旧语义复现和修正回归也按实际来源记录，作为评估方法改进实例。

后续复盘按“观察到的现象→解释依据→实际修改→验证结果”记录，并关联具体代码、运行结果和协作方式，使设计思路和改进结论可追溯。
