# 设计阶段反思

前半部分保留 P0 当时的设计思考，末尾补充 M1/M2 实际开发复盘。尚未发生的模型学习/优化不提前填写。

## 已识别的难点

最需要提前定义的是“完成”的含义：审核通过、候选空闲、草稿保存、用户确认是不同事实。将它们合成一个 success 会掩盖硬性时间被擅改或保存误报。

第二个难点是查询结果具有时效。查询时空闲不能保证保存时仍空闲，确认旧草稿也必须重新检查当前资料与占用。因此保存与确认都要在同一事实源内完成原子复核。

第三个难点是重试不等于可以沿用旧结论。重复请求需要防止新增草稿，但规则、素材或既有排期变化仍应重新核验。

文档核对中还识别到一个时间指纹问题：等价 UTC 时刻可能使用不同偏移，而缺省搜索范围取决于原始日历日。设计已要求把解析后的有效窗口纳入指纹，避免误把不同业务范围视作同一请求。

## 设计取舍

选择单 Agent、CLI 与 SQLite，使业务正确性、决策记录和验证可以集中完成。用户已确认在 CLI 核心之后补本地轻量网页；真实发布、多 Agent、分布式运行仍不进入首版范围。

收口检查发现，最初 20 次固定工具上限不足以支持 20 项普通流程。现已按项数推导预算并保留硬上限；这是设计算式修正，尚未验证实际模型耗时或成功率。

## 下一步

原设计顺序为契约与确定性规则、工具/存储、离线循环、真实模型与完整证据。当前 M1/M2 已完成，下一阶段为 M3。

## M1/M2 实际收获

M1 最难的是请求身份与时间语义：等价 UTC 表示在显式窗口下相同，但缺省搜索日历日可能不同。实现以有效默认日期参与指纹，测试同时约束创建与重新规划。

M2 最难的是区分保存事实、当前可用性和本次尝试：旧草稿存在不代表新写入成功，回执丢失也不代表确定失败。实现让草稿/占用/审计/精确操作回执同事务提交，按本次 operation_id 查证；无法查证返回 UNKNOWN，复用请求身份重试。

实际双线程测试在双方都完成查询后再竞争写入，证明事务必须重新查冲突。待确认草稿不占全局容量，确认时再竞争；这也说明展示“建议时段”不能写成“已锁定”。

本轮检查发现只用资料代次表示排期版本会遗漏本地新增占用；现用资料与可见占用的指纹。另一个修正是审核观察标记必须比较当前快照，不能因会话曾检查过就把新资料审核投影成已观察。测试保留这些回归。

技术取舍是把小型整体导入资料存为单份校验快照，事务逻辑留在 SQLiteStore 的小接口后面，而非预建多个空适配层。若资料规模和增量更新需求增长，再根据实际查询和性能证据拆表。

目前有 113 个方法和 7 组真实工具案例，但没有模型决策成功率、耗时优化或真实内容安全效果结论。M3 将重点验证观察如何改变动作、预算如何中止循环、Trace 丢失如何如实报告；M4 再验证真实模型并记录失败。
