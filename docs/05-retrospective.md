# 设计取舍与改进复盘

本文归纳项目在设计、实现和验证中形成的结论，以实际问题和证据组织；个人参与及AI辅助范围统一见 [04-ai-usage](04-ai-usage.md)。当前应用0.6.0，最终验收代码基线为e89b238；历史阶段报告保留其原提交边界。

## 业务问题如何影响设计

内容团队需要的结果是“哪些素材可以形成草稿、哪些必须补资料或确认、哪些需要阻断”。单一success无法表达这些差异：审核通过不等于时段可用，查询空闲不等于已经预留，草稿保存也不等于发布。

因此项目将审核结论、原始要求、候选时间、待确认项、草稿状态、保存尝试及执行状态分开表达。这样才能核对一次失败运行中是否客观存在已保存草稿，以及一个保存成功的建议是否仍待用户同意。

## 核心设计决策与代价

|业务或工程问题|项目选择及原因|代价与边界|
|---|---|---|
|如何明确展示模型决策|原生单Agent、有界循环、每轮一个工具动作；实际观察回传模型|需要自行处理工具协议和Trace；没有多Agent协作需求|
|怎样兼顾易运行和一致性|Python标准库、CLI、单机SQLite；核心完成后复用用例补本地网页|适合单用户本地验收；未验证分布式或生产规模|
|模型能否改变用户要求|模型只提出候选；硬性时间变更与人工风险由用户针对草稿版本逐项同意|交互需要明确确认；旧版本同意不能自动迁移|
|怎样处理查询后的并发变化|保存和确认在写事务内重新核对审核证据及占用|增加复核开销；用户确认时可能因新冲突被拒绝|
|怎样同时实现防重复与重新规划|同请求项唯一草稿；同请求不同输入拒绝；来源变化后沿用ID、增加版本并重置旧授权|调用方必须正确管理request_id；不同请求ID不做语义去重|
|待确认建议是否占容量|待确认草稿不占全局容量；READY草稿预留本地时段|建议可能在确认前被占用，因此不能把候选描述成已锁定|
|保存响应丢失能否直接报失败|保存草稿、预留、审计、操作回执同事务；按本次operation_id查证，无法确认则UNKNOWN|需要保留更多状态并支持原请求重试；UNKNOWN不能包装成成功|
|如何选择审核范围|先做元数据与文案，以规则及原文片段为依据，保留媒体扩展设计|覆盖范围清楚，但不证明视觉或完整内容安全审核|

一个具体例子：用户硬性要求18:00，被占用后模型建议19:00。系统保留原18:00并形成TIME_CHANGE待确认草稿；只有用户明确同意当前版本、事务再次验证可用后才能成为READY，整个过程仍未发布。新增19:00占用后，同请求重新规划到20:00，沿用草稿ID并更新版本，不能沿用之前的同意。实际输入、输出和Trace见 [评估文档](03-evaluation.md)。

## 最难的问题：业务事实与执行状态如何同时准确

旧草稿存在，不代表本次保存成功；回执丢失，也不代表数据库里没有草稿。运行中还可能出现“草稿已保存，但后续Trace写入失败”。若把这些情况合并成一个成功或失败，容易产生保存误报和错误重试。

项目分别保留business_task_status、save_attempt、execution_status和trace_complete，并使用精确操作回执对账。UNKNOWN案例最初预期为FAILED，实际顶层是PARTIAL，因为数据库中确实存在草稿，而当前保存尝试无法确认。修正评估预期时继续保留UNKNOWN、退出码和实际行数断言，原始差异也予以保留。这里调整的是对状态语义的理解，没有修改业务结果来迎合测试，见 [M3验收](M3-ACCEPTANCE.md)。

## 实际发现、定位、修正与验证

|现象|定位及修改|验证与收获|
|---|---|---|
|只用资料代次表示时段版本，遗漏本地新增预留|将资料与可见占用纳入指纹；审核观察标记与当前快照匹配|新增占用及来源变化回归；重复请求仍要核对当前事实，见 [M2](M2-ACCEPTANCE.md)|
|HTTP/1.0正文正常结束后，被误报为连接失败|响应完成时底层socket可能已关闭；识别正常结束并继续拒绝截断正文|保留首轮失败日志、复跑回环协议和真实路径，见 [M4](M4-ACCEPTANCE.md)|
|资料变化后页面仍停留旧状态|STALE_REVIEW未映射为409；补充错误映射及确认失败后的账本刷新|实际浏览器及回归复测；旧版本确认保持禁用，见 [M5](M5-ACCEPTANCE.md)|
|网络结果未知时，旧提交覆盖新编辑的要求或模式|保留原提交身份与模式，查询/重试原操作使用独立入口|修改输入和模式的Node控制器用例，见 [M6](M6-ACCEPTANCE.md)|
|后台终态写入失败，运行一直显示RUNNING|异常路径再次依赖同一故障journal；增加进程内实际结果投影及显式POST对账，GET只读|终态故障/恢复用例；额外暂停正常写入，避免将正常短暂窗口误判为中断，见 [M6](M6-ACCEPTANCE.md)|
|迟到的旧运行响应混入当前Trace|按运行ID和加载代次隔离响应，事件按序号去重|延迟旧元数据、旧事件和并发刷新用例；界面数据也需要身份约束，见 [M6](M6-ACCEPTANCE.md)|
|旧阶段验证脚本可能重写历史结果|增加版本保护，新验证使用独立目录|旧阶段导出和验证入口回归；证据也必须有版本边界，见 [M6](M6-ACCEPTANCE.md)|

M6修复前原有214个测试已通过，新增场景仍发现上述问题。这说明测试数量不能替代对业务状态、异步返回和故障边界的分析。有效验证需要先描述“什么情况下会错”，再构造能区分正确与错误实现的断言。

## 验证方法上的收获

1. 区分协议、模型决策和业务事实。回环HTTP证明协议处理；真实服务回执与实际观察链证明模型动作；SQL核对证明最终保存及确认事实。
2. 用变化检验行为。相同请求重复应复用；外部占用变化后应重新规划；错误确认版本应拒绝。对照变化前后，比只展示一次成功更有说明力。
3. 执行上限必须在派发前检查。模型换一个公开理由不能重置重试次数；20项正常Mock路径实际使用81次工具，支持按项数推导预算，仍不能保证任意组合完成。
4. 工具调用ID应保持原生对应。服务返回的tool_call_id与回传观察匹配，不能用客户端合成历史代替真实模型选择。
5. 检查实际运行模式。浏览器工具第一次未成功选择真实选项，运行保持Mock；将其单列，随后用全新账本确认real后重跑。意图不等于实际执行。

最终独立验收从干净源码和全新安装开始，222个Python测试方法及7项Node用例通过；8次真实CLI和2次真实网页运行共51次调用，逐层核对动作、原生回执、Trace与SQL事实。有限合成样本不支持通用成功率结论。证据入口见 [最终验收](FINAL-ACCEPTANCE.md)。

## 下一步

优先扩展不同文案、占用组合、工具错误及重复运行，分别统计业务完成、硬性要求越权和保存误报。已有合成用例全部符合预期，仍需更广的样本才能评估稳定性。

媒体扩展需要新增实际视觉证据、检查覆盖标记和独立验收；多人认证及外部平台容量按新需求设计。进程内终态缓存只用于当前进程降级，不提供断电保证；本地READY预留也不等于真实平台锁定。真实发布仍不在当前项目范围内。

个人投入约4小时（估算，未连续计时）。后续结合实际输入、输出和代码持续复盘，将设计判断、验证发现和改进过程与具体证据关联，见 [协作记录](04-ai-usage.md)。
