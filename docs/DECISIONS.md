# 设计决策清单

范围决定记录日期：2026-10-29。两项决定已生效；用户随后要求下一步，当前已完成 M1，见 STATUS。

## 1. 用户已选择的范围

用户通过问题卡明确选择以下两项；当时仅确定设计范围，后续另以“下一步”进入 M1。不得把范围选择的历史时间与实现进度混写。

|ID|问题|建议|其他选择|当前状态|
|---|---|---|---|---|
|D01|审核覆盖深度|元数据与文案；预留图片/视频扩展设计|加入图片审核；加入视频审核|用户已选择建议方案|
|D02|最终展示方式|CLI 核心完成后，补轻量网页工作台|仅 CLI 与可读报告|用户已选择建议方案|

D01 的影响：

- 元数据与文案：版权、字段完整性、渠道适配、文案风险。可以使用合成资料，审核能力边界容易复核。
- 图片：需要视觉模型或图像检查工具，定义图片证据定位与失败行为；不能用元数据测试代替视觉审核效果。
- 视频：另需文件读取、采样/字幕或音轨处理、时间片段证据、耗时与模型预算设计；不能把抽帧结果称为完整视频审核。
- 无论选哪层，确认、幂等、冲突与保存保护保持一致；没有实际检查到的内容不能标成已审核。

D02 的影响：

- 网页工作台：展示素材列表、风险证据、冲突建议、待确认事项和 Trace；确认与保存仍走同一应用用例。
- CLI 与报告：保留相同业务能力和全部证据，减少前端设计工作。
- CLI 始终保留为可复制的验收入口；选择网页不把测试依赖绑在手工点选上。

当前已补 [文案审核](design/content-review.md)、[网页工作台](design/workbench.md) 和 [媒体扩展边界](design/media-extension.md)。视觉部分只预留设计，不新增实现或依赖；网页在 CLI 核心完成后再实现。

## 3. 由项目设计处理的默认方案

下列不是用户已经逐项确认的业务事实，而是当前可审查、可调整的设计选择；不要求用户审批每个技术细节。

|设计选择|理由与后续验证|
|---|---|
|Python、SQLite、单 Agent、原生有界循环|缩小外部依赖，便于验证状态与事务；实现后复现|
|四种状态分开输出|审核、时段、草稿、保存不能互相冒充|
|READY 草稿占本地容量，待确认不占全局容量|体现有效方案与建议的差别；确认时重新查冲突|
|同批待确认项互相避让|交付的同一份建议方案内部不应冲突|
|确认绑定草稿版本和逐项待确认 ID|防止旧同意授权新方案|
|默认不跨原始时间所在日历日建议|避免扩大缺省搜索范围；调整仍待确认|
|稳定请求 ID 与规范化指纹|同请求可重试，换内容不可覆盖|
|保存与确认事务内复核|解决查询后占用变化，避免虚报成功|
|按实际数据组装结果|模型结束文本不能控制成功状态|

如后续样例或用户选择推翻某项假设，先同步需求、契约、状态与测试计划，再进入实现。

## 4. 本轮补充澄清

1. 请求中的 `duration_minutes` 是排期占用长度，不是视频播放时长。首版容量规则属于合成排期业务假设。
2. 人工接受可确认风险不会把审核事实改成 PASS；原风险、证据与接受记录都保留。
3. 用户补齐素材资料可以在同一业务请求下重新审核；修改原始发布时间或允许窗口应使用新请求。
4. 网页、CLI、未来其他入口共享相同确认与保存约束，不能各写一套判断。
